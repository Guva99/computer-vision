# План рефакторинга: привести архитектуру в порядок, не сломав поведение

Версия 2 (2026-10-27). Отличие от версии 1: цель не только «стало чище», а
**готовые точки врезки** под следующую статью — реальный техпроцесс, вторая
камера, категорийно-независимая сегментация. План выстроен так, чтобы после него
каждое из этих трёх дополнений добавлялось как компонент, а не как форк кода.

Для того, кто будет это делать (автор проекта или сессия Claude).
Методология экспериментов — [EXPERIMENTS.md](EXPERIMENTS.md), команды —
[VALIDATION.md](VALIDATION.md), журнал стенда — [STAND_NOTES.md](STAND_NOTES.md).

## Правило №1: поведение не меняется, и это ПРОВЕРЯЕМО

Проверено 2026-10-20 на записи `S04_cube_on_path/run_01_3d`:

```
playback-прогон #1 : 177 кадров, 12 DANGER / 17 WARN / 148 SAFE
playback-прогон #2 : идентичен #1 бит-в-бит (frame, level, min_dist_m, focus_part, n_objects)
прогон на СТЕНДЕ   : decisions.csv совпадает с playback ПОЛНОСТЬЮ (177/177 строк)
```

`source_mode=playback` — **детерминированный оракул**. Любой шаг, не меняющий
алгоритм, обязан оставить `decisions.csv` побитово тем же. Локально доступно
**41 запись** с кадрами.

Правила работы:

1. ни один шаг не меняет пороги, гейты и порядок вычислений — только структуру;
2. после каждого шага — регрессия по golden-набору; расхождение = откат сразу;
3. один шаг = один коммит. Шаги, не проверяемые регрессией, помечаются
   `behaviour-change:` — таких в плане два (S1.4 и S3.5).

Для статьи это важно: идентичность `decisions.csv` на уже собранных записях —
доказательство, что метод не поменялся, то есть требование «параметры
зафиксированы до прогонов» остаётся выполненным.

## Пять точек врезки, которые должны появиться

Это приёмочный критерий всего рефакторинга. После него каждый пункт следующей
статьи должен делаться так:

| Что нужно для следующей статьи | Как должно выглядеть ПОСЛЕ рефакторинга |
|---|---|
| **1. Нейросегментация** вместо яркостной | `segmenter = "neural"` в конфиге; новый класс реализует тот же порт; старый путь остаётся как fallback |
| **2. Вторая камера** | список источников кадров вместо одного; позднее слияние решений (`max` по уровням); межкамерная калибровка не нужна |
| **3. Модель задачи** (робот строит башни) | порт `TaskState` отдаёт ожидаемое состояние сцены; восприятие сравнивает наблюдение с ожиданием |
| **4. Быстрый/медленный контуры** | состав двух списков шагов; задержка останова зависит ТОЛЬКО от быстрого |
| **5. Абляция** (Э4, вклад каждого компонента) | состав списка шагов, а не флаги внутри кода; прогон на фиксированных записях |

Если после рефакторинга хоть один пункт требует правки `gripper_detection.py`
или `collision.py` — рефакторинг сделан не до конца.

## Гибкость: по каким осям открыто, по каким — жёстко

Цель — «добавление фич не вызывает сложностей». Но «готов к любым изменениям»
недостижим, и попытка его достичь делает код **менее** изменяемым: абстракция,
введённая на всякий случай, почти всегда оказывается не той, что потребуется, и
потом мешает. В этом проекте это уже произошло дважды, и оба раза измеримо:

| Что добавляли «для гибкости» | Чем обернулось |
|---|---|
| `getattr(cfg, "x", default)` — чтобы код работал с неполным конфигом | **125 мест, 16 молча разошлись** с AppConfig; абляция на частичном конфиге получит другой алгоритм |
| булевы переключатели режимов | **54 флага = 1.8·10¹⁶ конфигураций**, измерена ровно ОДНА. 15 ветвей выключены и не покрыты ничем: `collision_dbscan_adaptive_eps`, `collision_workspace_filter`, `depth_filters_enabled`, `wrist_use_static_roi`, `detect_gripper_from_manipulator_mask` и др. |

Это не гибкость, а непроверенная поверхность. Поэтому правило такое: **открыто по
названным осям, жёстко и просто везде остальное.**

| Ось изменений | Режим | Чем обеспечивается |
|---|---|---|
| источник кадров (камера / playback / вторая камера) | **открыта** | `FrameSource` + `factory`, S4.3–S4.4 |
| сегментатор (яркость / нейро / следующий) | **открыта** | `SegmenterPort`, S2.6 |
| состав конвейера коллизий (добавить, убрать, переставить шаг) | **открыта** | список шагов, S3.1 |
| политика безопасности (пороги, дебаунс, слияние контуров) | **открыта** | `SafetyController` + `fusion`, S3.4–S3.5 |
| модель техпроцесса | **открыта** | `TaskStatePort`, S4.5 |
| математика ядра (пинхол, плоскость, дистанции) | **жёстко** | меняется раз в годы — пусть будет простой функцией без абстракций |
| схема логов и записей | версионируется | поле `schema_version`, старые записи читаются |

Шестая ось понадобится — откроем тогда. С оракулом на 41 записи это дешёвая
операция, а не катастрофа. **Правило трёх:** абстракция вводится на третьем
реальном случае, не на первом; исключение — пять осей выше, они уже известны.

**Бюджет сложности, действует с этого момента:**

1. новый флаг добавляется только вместе с тестом или регрессией, которая его
   покрывает. Иначе не добавляется;
2. выключенная ветка либо покрывается регрессией, либо удаляется (S1.6);
3. новая абстракция — только под названную ось или на третий случай.

## Принципы как исполняемые правила, а не как обещания

Принцип, который нельзя проверить скриптом, через три месяца размывается. Поэтому
каждый проверяется в `pytest` (шаг S0.6), и нарушение роняет сборку:

| Принцип | Что сейчас | Чем будет обеспечен | Как проверяется автоматически |
|---|---|---|---|
| **SRP** | `collision.py` 1169 строк: детекция + рисование + логи + глобалы | разделение по слоям | метрики: файл ≤ 400 строк, функция ≤ 60, аргументов ≤ 5 или dataclass |
| **OCP** | новый сегментатор = правка `segmentation_service` и 38-аргументной функции | порты + списки шагов | тест: заглушка-сегментатор подключается **только** конфигом, в `pipeline.py` ноль правок |
| **LSP** | `PlaybackCamera` повторяет интерфейс камеры «по договорённости» | явные `Protocol` | **контрактный тест**, параметризованный по всем реализациям порта: камера, playback, нейро- и яркостный сегментатор проходят один и тот же набор |
| **ISP** | `cfg` с 267 полями передаётся всем | узкие порты + группы конфига | тест: playback реализует `FrameSource` без заглушек-`pass` |
| **DIP** | `fk_service` (робот) импортирует `collision` (зрение); `core`-логики нет | `core/` без cv2/o3d/SDK | тест запрещённых импортов: `core` не видит `cv2`, `open3d`, `pyrealsense2`; `robot` не видит `vision` |
| **DRY** | 125 getattr-дефолтов, высота над плоскостью в 4 местах, два вокселя | единый конфиг, `core/geometry.py` | скрипт-тест: ни одного `getattr(cfg, ..., default)`; дефолты существуют в одном месте |
| **KISS** | 54 флага, 1.8·10¹⁶ конфигураций | бюджет сложности выше | тест: число булевых флагов не растёт без покрытия |

Именно эти тесты и есть «готовность к изменениям»: они не дают архитектуре
разъехаться, когда через полгода правку делает уставший человек или сессия, не
читавшая этот документ.

## Целевая архитектура

```
main.py                   composition root: собирает всё по конфигу
  app/
    ports.py              Protocol: FrameSource, JointSource, RobotActuator,
                          SegmenterPort, TaskStatePort, DecisionSink
    factory.py            камера/playback, один источник или несколько, выбор сегментатора
    runner.py             цикл; железа в конструкторе нет
    pipeline.py           кадр → решение; собирает быстрый и медленный контуры
    fusion.py             позднее слияние решений по камерам (консервативный max)
  perception/
    fast/                 КАЖДЫЙ кадр: глубина в ROI, FK-капсула, дистанция, уровень
    slow/                 раз в N кадров: сегментация, идентификация, память объектов
  vision/                 алгоритмы CV (cv2 можно) — БЕЗ рисования и окон
    segmenters/           brightness.py (текущий) | neural.py (следующая статья)
  robot/                  FK, драйверы KUKA — НЕ зависит от vision
  task/                   модель техпроцесса: фазы, ожидаемое состояние сцены
  core/                   домен: numpy-геометрия, типы, политики. Без cv2/o3d/файлов
  adapters/               realsense, playback, csv-логи, overlay/o3d
  config/                 вложенные dataclass-группы + загрузка из YAML
```

Граница `core/` проверяется одним тестом: импортируется в процессе без
`pyrealsense2`, без `open3d` и без дисплея.

`cv2` в `vision/` разрешён (это библиотека алгоритмов). Запрещены `imshow`,
`drawContours`, `putText` и o3d-геометрия — они живут в `adapters/`.

## Критический путь до кампании следующей статьи

Если нужно начать снимать новые данные как можно раньше, обязательный минимум:

```
Фаза 0 (вкл. S0.6)  →  S1.1  →  S1.3  →  S1.6  →  S2.5  →  S2.6  →  S3.1  →  S3.2  →  S3.6  →  S4.4  →  S4.5
```

Это даёт: оракул и тесты, единый источник правды, подменяемый сегментатор,
абляцию составом списка, бюджет FPS под вторую камеру, запись двух потоков и
состояние задачи в логах. Остальное (S3.3, S3.4, S3.5 с `N>1`, S4.1–S4.3,
Фаза 5) можно делать параллельно с кампанией — оно не влияет на пригодность
данных.

**Чего нельзя откладывать ни при каком раскладе:** S4.4 и S4.5. Если кампания
пройдёт без записи второго потока и без состояния задачи, абляции «вклад второй
камеры» и «законное изменение vs вторжение» потребуют ПЕРЕСЪЁМКИ — а расстановки
между кампаниями не повторяются, это уже проверено на забракованном парном
прогоне «контроль/опыт».

## Чего делать НЕ надо

- **не переписывать `gripper_detection.py`** (1542 строки эвристик с подобранными
  на стенде константами) — только параметризация и перенос за порт;
- **не менять пороги, гейты и алгоритмы** в рамках рефакторинга: это обесценит
  41 собранную запись. Оптимизация стадии `masks` — отдельная задача после
  Фазы 3, и она проверяется регрессией как изменение поведения;
- **не вводить** DI-контейнер, абстрактные фабрики, репозитории, Event Bus,
  async: 267 полей конфига и 4–7 FPS — не те проблемы, которые они решают;
- **не ставить torch/openvino в рабочий venv стенда** — отдельное окружение;
- **не делать большой мерж**: ветка `refactor/clean-arch`, мерж фазами, после
  каждой — зелёная регрессия.
